# ADR-003: pgvector for V1 Vector Similarity Search

## Status

Proposed

## Context

Skill discovery requires retrieving candidate skills that are relevant to an agent's weakness
(see [Skill Discovery](../skills/skill-discovery.md)). This is a vector similarity problem.
V1 must remain operationally simple, and the project already plans PostgreSQL as its primary
database ([ADR-001](ADR-001-postgresql.md)). A key research distinction is that similarity is
*not* quality; retrieval only proposes candidates that are then validated by benchmarking.

## Decision

Use the pgvector extension for V1 vector similarity search, storing skill embeddings in the
primary PostgreSQL database.

## Rationale

- Keeps vectors alongside relational metadata, enabling filtering by permissions, trust, and
  version in a single query.
- Avoids operating a separate vector database in V1.
- Sufficient performance for V1 registry sizes.
- Integrates with the planned Prisma/raw-SQL access layer.

## Alternatives Considered

- **Dedicated vector databases (Pinecone, Weaviate, Qdrant, Milvus):** strong performance and
  features, but add a second stateful system and data-synchronization burden before scale
  requires it.
- **In-memory/ANN libraries (FAISS):** fast but require custom persistence and service
  integration; less natural for filtered retrieval over relational metadata.
- **No vector search (keyword/metadata only):** simplest, but insufficient for semantic discovery
  of relevant skills.

## Consequences

- Positive: one store for relational and vector data; filtered retrieval is straightforward.
- Negative: pgvector will not scale as far as dedicated vector stores; index tuning is required.
- Neutral: embeddings are generated by the AI/ML service
  ([ADR-004](ADR-004-fastapi-ai-service.md)).

## Revisit Conditions

- If registry size or query latency outgrows pgvector.
- If advanced vector features (multi-vector, complex ANN tuning) become necessary.
- If the system becomes distributed and a shared vector store is preferable.
